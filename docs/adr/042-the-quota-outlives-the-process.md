# ADR-042: The quota outlives the process, and Valkey leaves the stack

- **Status:** Accepted (supersedes the Valkey half of ADR-004)
- **Date:** 2026-09-24
- **Plan reference:** ADR-004, FR-3.7, SR-3.2, SR-X.27, §19.2

## Context

Two facts that turn out to be the same fact.

**One.** `apps/api/src/plugins/quota.ts` kept the published API allowance — 60 requests a
minute and 1,000 a day per key — in two `Map`s, with a comment saying the counter moves to a
shared store "the day a second API container exists".

That trigger is correct for _sharing_ a limit between processes and wrong for _keeping_ one.
A counter in memory does not only fail to be shared; it fails to exist across a restart. And
a restart is not a rare event, it is every deploy. So "1,000 requests per day" has actually
meant **"1,000 requests since the API last started"** — on one instance, today, with no second
container anywhere in sight. The daily quota was not waiting on a scaling decision. It was
already wrong.

**Two.** Valkey has been running in the dev and production stacks since Phase 0, with a
generated password, a persistent volume, an append-only file, a health check, and four Linux
capabilities added back so it could take ownership of its data directory.

Nothing connects to it. Not one line in `apps/` or `packages/` opens a connection; `VALKEY_URL`
is generated by `scripts/init-env.sh`, written into `.env`, shipped to the server and encrypted
in SOPS, and is read by no code at all. BullMQ is not a dependency. The rate limiter, the
quota, the flag cache and the sign-in throttle are all in process memory or in Postgres.

It was worse than idle. The documents describe it as real: `docs/runbooks/backups.md` says it
is not backed up because "it holds only caches and rate-limit counters", and
`docs/runbooks/key-rotation.md` says rotating its URL "resets cache and rate-limit counters".
Both describe a system that does not exist. Anyone reading the infrastructure would conclude
the limits are shared and durable. They were neither.

And it was load-bearing in the one direction nobody wanted. `infra/vps/deploy.sh` brings the
stack up with `docker compose up -d --wait`, which waits on **every** service before declaring
success, with an `ERR` trap that rolls back on failure. A Valkey that failed to start — a bad
pull, a corrupt append-only file, a full disk — would have failed the deploy and rolled back a
perfectly healthy release. An unused dependency could take the site down and could do nothing
else.

## Decision

### The two windows have different homes, because they are different kinds of thing

| Window         | Home     | Why                                                                                                                                                              |
| -------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Per minute** | Memory   | A rate limit. Losing it on restart costs at most one minute of burst control, which nobody can plan around, and being in memory is what makes it free to check.  |
| **Per day**    | Postgres | An accounting fact. A published daily allowance that refills whenever the process restarts is not a quota, and deploys are frequent and observable from outside. |

Two new columns on `app.api_keys` (`quota_day`, `quota_used`) and one statement that counts:

```sql
update app.api_keys
   set quota_day  = timezone('utc', now())::date,
       quota_used = case when quota_day = timezone('utc', now())::date
                         then quota_used + 1 else 1 end
 where id = $1
returning quota_used
```

One statement rather than a read and a write, because between those two any number of requests
can pass; the row lock is what serialises concurrent callers holding the same key. The
roll-over lives **inside** the statement — the `CASE` reads the old `quota_day` — so there is
no sweeper, no scheduled job, and no key quietly carrying yesterday's count. The day is UTC and
explicitly so, since `current_date` would otherwise follow the connection's TimeZone and make a
published limit depend on a container's environment. It is also now a real calendar day rather
than 24 hours from some forgotten first call.

### Order is part of the design

The minute is checked first, in memory. A caller already over it is refused without the
database being touched at all — which is both the cheap answer and the thing that bounds how
often the durable counter can be written: at most `perMinute` writes per key per minute, by
construction. The cheap limit protects the expensive one.

### The database is the authority, memory is the floor

The day total is `max(durable, in-process)`. This needs no branch on failure and is right in
both directions: with the database up its count always leads, and if the counting statement
fails the process still enforces what it has seen rather than nothing at all. A bookkeeping
outage must not become an availability outage, and it must not become an open door either.

The column grant follows migration 0017's shape: the worker role may `UPDATE (quota_day,
quota_used)` and still may not re-scope a key or un-revoke one. The web role may **read** the
counter, for the developer console, and may not write it — the tier that takes session traffic
cannot reset somebody's quota.

### Valkey comes out of both stacks

Removed from `docker-compose.dev.yml` and `docker-compose.prod.yml`, from `init-env.sh`,
`.env.example`, the rehearsal and verification scripts, and from the documents that described
it as doing work.

It comes back when something needs it, and the trigger is written down rather than discovered:

- **a second API or web instance**, where an in-memory minute window stops being one window; or
- **a real job queue** — BullMQ for alert fan-out, whenever the one-shot job containers stop
  being enough.

Either is a deliberate change with its own ADR. Neither is served by having the container
running in the meantime.

## Consequences

- The daily quota is now the number the documentation claims, across restarts and deploys.
- One request per key per request against Postgres, bounded by the minute window at 60 per key
  per minute, on the same pool and the same narrow grant that already verified the key.
- The production stack has one fewer container, one fewer volume, one fewer password in the
  encrypted environment, one fewer third-party image to keep patched, and one fewer service
  that could fail a deploy.
- A restore now restores everything that held state, rather than everything plus a volume of
  nothing.
- **Bringing a shared store back is real work again**, deliberately. That is the honest cost:
  the day it is needed, it is an ADR, a dependency and a deployment — rather than a connection
  string that was lying in wait.

## Alternatives considered

**Wire the existing Valkey in.** It is running; use it. But it would have meant a new
dependency, a new failure mode and a new connection to secure, to solve a problem Postgres
already solves for a table it already owns — and at the volumes in question, "one more row
update on a row we are already updating" beats "one more datastore". Sharing between instances
is the thing Valkey is actually for, and there are no instances to share between.

**Leave the quota in memory and remove Valkey only.** This was the tempting small change, and
it would have left the published limit wrong. The two findings arrived together because they
have the same cause — a control that was believed rather than checked — and fixing one without
the other would have removed the evidence while keeping the bug.

**Keep Valkey "for Phase 5".** A service kept for a phase that has not started is a service
nobody monitors, nobody patches deliberately, and nobody notices has failed. The plan is not a
reason to run software; needing it is.
